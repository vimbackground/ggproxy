# ggproxy 一键自动化部署操作指南

本文档面向希望通过 GitHub 集成快速完成部署的用户。平台顺序固定为：Cloudflare → Vercel → Deno → Netlify。

## 1. 使用前须知

通过 GitHub 集成部署通常会完成以下操作：

1. 登录目标云平台。
2. 选择你已有的 GitHub 仓库。
3. 创建应用并完成首次构建。
4. 建立 GitHub 持续部署；后续推送自动发布。

为避免公开代理被滥用，首次部署完成后至少应配置：

```text
PROXY_TOKEN=<高强度随机令牌>
```

如希望客户端不再传 Gemini Key，再配置：

```text
GEMINI_API_KEYS=<一个或多个Gemini API Key>
```

所有密钥都应使用平台的 Secret 功能，不能写进 Git 仓库、部署链接查询参数或普通配置文件。

## 2. Cloudflare 自动部署（连接当前仓库）

不要使用 Cloudflare 的 `Deploy to Cloudflare` 按钮。该按钮的设计就是把公开源仓库复制到你的 GitHub/GitLab 账户后再部署，因此会新建一个类似 `GG-proxy` 的仓库。

请在 [Cloudflare Workers & Pages](https://dash.cloudflare.com/?to=/:account/workers-and-pages) 中连接你当前正在使用的 GitHub 仓库。首次连接后，后续推送会自动部署，并且不会创建新的 GitHub 仓库。

### 操作步骤

1. 打开 Workers & Pages，选择 **Create application** → **Import a repository**。
2. 授权 Cloudflare 访问 GitHub；仅授予当前仓库（或其所在 Organization）访问权限。
3. 在仓库列表中选择你当前的 `ggproxy` 仓库和生产分支（通常是 `main`）。
4. Worker 名称填写 `g2g`，与本仓库 [`wrangler.toml`](../wrangler.toml) 的 `name` 保持一致。
5. 保持部署命令为 `npx wrangler deploy`，保存并部署。
6. 打开 Worker：`Settings` → `Variables and Secrets`。
7. 以 `Secret` 类型添加 `PROXY_TOKEN`，按需添加 `GEMINI_API_KEYS`。
8. 保存；以后向所选仓库的生产分支推送代码即可自动发布。

Cloudflare Workers Builds 可以连接已有 Worker 或在创建时直接选择已有仓库；不会复制或新建 GitHub 仓库。Workers Builds 默认使用 `npx wrangler deploy`，本项目无需额外构建命令。

### 自动更新

向刚才选择的当前 GitHub 仓库生产分支推送代码：

```bash
git push origin main
```

Cloudflare 将自动构建并发布；非生产分支可生成预览版本，具体取决于 Builds 设置。

## 3. Vercel 一键部署

[![Deploy with Vercel](https://vercel.com/button)](https://vercel.com/clone?repository-url=https%3A%2F%2Fgithub.com%2Fvimbackground%2Fggproxy&env=PROXY_TOKEN%2CGEMINI_API_KEYS&envDescription=Set%20a%20gateway%20token%20and%20Gemini%20API%20key%20pool.%20Store%20both%20as%20secrets.)

直接地址：

```text
https://vercel.com/clone?repository-url=https%3A%2F%2Fgithub.com%2Fvimbackground%2Fggproxy&env=PROXY_TOKEN%2CGEMINI_API_KEYS&envDescription=Set%20a%20gateway%20token%20and%20Gemini%20API%20key%20pool.%20Store%20both%20as%20secrets.
```

### 操作步骤

1. 点击按钮并登录 Vercel。
2. 选择 GitHub 账号，填写新仓库和项目名称。
3. 在部署页面填写 `PROXY_TOKEN` 和 `GEMINI_API_KEYS`。
4. 点击 `Deploy`。
5. 等待构建完成，打开分配的 `*.vercel.app` 地址。

Vercel 官方不允许在 Deploy Button URL 中直接传入密钥值；按钮只声明变量名称，敏感值由你在部署页面输入。

### 自动更新

Vercel 创建的项目会连接生成的 GitHub 仓库：

- 生产分支提交自动创建 Production Deployment。
- 其他分支和 Pull Request 自动创建 Preview Deployment。
- 如修改环境变量，重新部署最新 Production Deployment。

## 4. Deno 快速部署与自动化

> Deno Deploy Classic 已于 2026-07-20 停止。新版平台使用 [console.deno.com](https://console.deno.com) 和 `deno deploy`，不要使用旧的 `dash.deno.com` 或 `deployctl` 链接。

Deno 新平台目前以 `New App + GitHub integration` 作为官方快速流程，没有与前三个平台完全等价的通用公开 Deploy Button。因此这里提供最短 Dashboard 流程和单条 CLI 创建命令。

### Dashboard 快速流程

1. 打开 [Deno Deploy Console](https://console.deno.com) 并登录。
2. 进入 Organization，点击 `+ New App`。
3. 选择 `vimbackground/ggproxy` 或你的 Fork。
4. 将运行模式设为 `Dynamic`，入口设为：

```text
src/deno_index.ts
```

5. 添加 Secret：`PROXY_TOKEN` 和可选的 `GEMINI_API_KEYS`。
6. 点击 `Create App`。

### CLI 单命令创建

安装并登录最新版 Deno 后执行：

```bash
deno deploy create \
  --source github \
  --owner vimbackground \
  --repo ggproxy \
  --runtime-mode dynamic \
  --entrypoint src/deno_index.ts
```

随后在 Dashboard 中添加 Secret，或使用：

```bash
deno deploy env add PROXY_TOKEN "你的随机令牌" --secret
deno deploy env add GEMINI_API_KEYS "你的Gemini-Key" --secret
```

如果 CLI 无法自动确定目标应用，根据提示指定 `--org` 和 `--app`。

### 自动更新

应用与 GitHub 仓库连接后，每次 Push 都会触发新的构建和 Revision。Dashboard 中也可以使用 `Deploy Default Branch` 手动重跑默认分支。

## 5. Netlify 一键部署

[![Deploy to Netlify](https://www.netlify.com/img/deploy/button.svg)](https://app.netlify.com/start/deploy?repository=https://github.com/vimbackground/ggproxy#PROXY_TOKEN=&GEMINI_API_KEYS=)

直接地址：

```text
https://app.netlify.com/start/deploy?repository=https://github.com/vimbackground/ggproxy#PROXY_TOKEN=&GEMINI_API_KEYS=
```

### 操作步骤

1. 点击按钮并登录 Netlify。
2. 选择 GitHub 账号，确认新仓库和站点名称。
3. 填写 `PROXY_TOKEN` 和 `GEMINI_API_KEYS`。
4. 点击 `Save & Deploy`。
5. 等待函数构建完成，打开分配的 `*.netlify.app` 地址。

链接中的环境变量位于 URL fragment（`#` 后），由浏览器端处理，不会作为普通查询参数发送到 Netlify 服务端。即便如此，也不要把真实密钥直接写入可分享的链接；应在表单内填写。

### 自动更新

Netlify 一键流程会连接生成的 GitHub 仓库。后续执行：

```bash
git push origin main
```

即可触发新的 Production Deploy。Pull Request 可按站点配置生成 Deploy Preview。

## 6. 一键部署后的统一检查

### 6.1 健康检查

```bash
curl https://你的部署域名/healthz
```

期望状态码为 `200`，并返回：

```json
{"name":"ggproxy","status":"ok","protocols":["gemini","openai","anthropic"]}
```

### 6.2 安全检查

- 请求不携带 `x-proxy-token` 时，应返回 `401 invalid_proxy_token`。
- 平台日志中不应出现 Gemini API Key 或完整 Authorization。
- `/verify` 默认应返回 404。
- 未配置浏览器调用时，保持 `CORS_ORIGINS` 为空。

### 6.3 OpenAI 格式测试

如果已经设置服务端 Key 池：

```bash
curl "https://你的部署域名/v1/chat/completions" \
  -H "x-proxy-token: 你的网关令牌" \
  -H "content-type: application/json" \
  -d '{"model":"gemini-2.5-flash","messages":[{"role":"user","content":"reply only: ok"}]}'
```

如果没有设置服务端 Key 池，再添加：

```http
Authorization: Bearer 你的Gemini-Key
```

## 7. 更新与回滚

### 自动更新

四个平台连接 GitHub 后，通常只需向生产分支 Push：

```bash
git pull
git push origin main
```

Cloudflare 使用的是你在 Workers Builds 中选定的仓库；确认 `origin` 指向该仓库后再推送。

### 回滚

- Cloudflare：在 Worker 的 Deployments/Versions 中选择上一版本重新部署。
- Vercel：在 Deployments 中打开已验证版本并 Promote/Redeploy。
- Deno：在 App 的 Revisions/Builds 中选择先前 Revision。
- Netlify：在 Deploys 中选择先前成功部署并发布。

回滚代码不会自动恢复后来修改的环境变量；如果故障与 Secret 或配置有关，需要单独恢复对应值。
