# ggproxy 手动部署操作手册

ggproxy 的正式部署范围是 Cloudflare Workers 和 Vercel Edge。两者使用同一套环境变量、接口路径和后台；Deno 与 Netlify 没有独立部署方案。

## 1. 部署前准备

准备 GitHub 仓库、Node.js 18+，以及 Cloudflare 或 Vercel 账号。请在平台的 Secret / Environment Variables 中配置敏感值，不要提交到仓库。

| 变量 | 是否必需 | 作用 |
|---|---|---|
| `GEMINI_API_KEYS` | 普通用户模式必需 | 服务端 Gemini Key；多个 Key 用逗号分隔 |
| `PROXY_TOKEN` | 可选 | 一个旧版静态网关令牌，继续使用 `x-proxy-token` 调用 |
| `PROXY_TOKENS` | 可选 | 多个静态网关令牌，逗号分隔 |
| `ADMIN_TOKEN` | 启用后台时必需 | `/admin` 的登录令牌 |
| `DEFAULT_GEMINI_MODEL` | 否 | 非 Gemini 模型名映射的默认模型，默认 `gemini-2.5-flash` |
| `CORS_ORIGINS` | 浏览器跨域调用时需要 | 精确 Origin 列表，逗号分隔 |

不要把 `GEMINI_API_KEYS`、`ADMIN_TOKEN`、KV 写入令牌或用户令牌放进源码、截图或聊天记录。

## 2. Cloudflare Workers

仓库已包含 `wrangler.toml` 和 Worker 入口 `src/index.js`。

```bash
git clone https://github.com/vimbackground/ggproxy.git
cd ggproxy
npm install
npx wrangler login
npx wrangler deploy
```

在 **Workers & Pages → ggproxy → Settings → Variables and Secrets** 中添加上述变量。使用服务端 Key 池时至少添加 `GEMINI_API_KEYS`。

### 启用后台令牌管理（可选）

1. 在 Cloudflare Dashboard 创建一个 Workers KV namespace，例如 `ggproxy-admin`。
2. 在 Worker 的 **Bindings** 中添加 KV Namespace Binding：变量名必须是 `GGPROXY_ADMIN_KV`，值选择刚创建的 namespace。
3. 添加 Secret `ADMIN_TOKEN` 和 `GEMINI_API_KEYS`，重新部署后打开 `https://你的域名/admin`。

Workers KV 绑定支持由 Worker 读写键值；后台只在其中保存客户端令牌的哈希和名称，不保存 Gemini Key。参考 [Cloudflare Workers KV 写入文档](https://developers.cloudflare.com/kv/api/write-key-value-pairs/)。

## 3. Vercel Edge

仓库的 `vercel.json` 已将所有路径转发到 Edge 入口 `api/vercel_index.js`。

1. 在 [Vercel Dashboard](https://vercel.com/new) 选择 **Add New → Project**，导入当前仓库。
2. Framework Preset 选择 `Other`，Root Directory 保持仓库根目录；不填写 Build Command 和 Output Directory。
3. 在 Environment Variables 添加 `GEMINI_API_KEYS`，以及按需的其他变量。
4. 点击 Deploy，随后访问 `https://你的域名/healthz`。

### 启用后台令牌管理（可选）

后台需要可由 Edge 访问的 KV。创建一个兼容 Upstash REST API 的 Redis/KV 后，在 Vercel 环境变量中设置：

```text
ADMIN_TOKEN=高强度随机值
ADMIN_KV_REST_URL=https://你的-kv-rest-地址
ADMIN_KV_REST_TOKEN=有写入权限的令牌
```

也兼容 `UPSTASH_REDIS_REST_URL` / `UPSTASH_REDIS_REST_TOKEN` 和 `KV_REST_API_URL` / `KV_REST_API_TOKEN`。REST KV 通过 HTTP 运行，适合 serverless/edge 环境；写入令牌只能保存在 Vercel 的服务端环境变量中。参考 [Upstash REST API 文档](https://upstash.com/docs/redis/features/restapi)。

## 4. 部署后检查

```bash
curl https://你的域名/healthz
```

应返回 `200` 和 `status: ok`。如果配置了 `GEMINI_API_KEYS`，可再用 OpenAI 路径测试：

```bash
curl https://你的域名/v1/chat/completions \
  -H "Authorization: Bearer 你的Gemini-Key" \
  -H "content-type: application/json" \
  -d '{"model":"gemini-2.5-flash","messages":[{"role":"user","content":"reply only: ok"}]}'
```

如使用后台生成的用户令牌，请改用该令牌作为 Bearer Token；前提是已配置 `GEMINI_API_KEYS`。可参阅 [Kelivo 用户使用教程](Kelivo用户使用教程.md)。

## 5. 常见问题

### `/admin` 返回 404

未设置 `ADMIN_TOKEN`，这是默认行为。

### 后台提示需要管理存储

Cloudflare 检查是否已绑定 `GGPROXY_ADMIN_KV`；Vercel 检查 `ADMIN_KV_REST_URL` 与 `ADMIN_KV_REST_TOKEN` 是否同时存在。

### 用户令牌调用返回 `missing_api_key`

用户令牌只用于网关认证。请在部署平台设置 `GEMINI_API_KEYS`，不要把 Gemini Key 发给普通用户。

### 用户令牌调用返回 `invalid_proxy_token`

令牌可能填错、已撤销，或请求没有使用 `Authorization: Bearer 用户令牌`（部分客户端也可使用 `x-proxy-token`）。
